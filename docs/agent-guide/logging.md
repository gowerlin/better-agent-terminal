# Logging

> 從 CLAUDE.md「Logging」節搬出（T0595）。本檔為該節完整原文；CLAUDE.md 該節保留用途、必守規則、唯一實作位置與本檔連結。

- **Frontend (renderer)**: Use `window.electronAPI.debug.log(...)` instead of `console.log()`. This sends logs to the electron main process logger, which writes to disk.
- **Backend (electron)**: Use `logger.log(...)` / `logger.error(...)` from `./logger`.
- Do NOT use `console.log()` for debugging — use the logger so logs are persisted and visible in the log file.
- **Log file location**: `<appData>/BetterAgentTerminal/Logs/debug-<YYYYMMDD-HHMMSS>.log`（每次啟動一檔，保留最近 10 個；`electron/logger.ts`）。`<appData>`：Windows `%APPDATA%`、macOS `~/Library/Application Support`、Linux `~/.config`。磁碟日誌**預設開啟**（Settings → Advanced → Debug Logging 可關 / 調等級），與 `BAT_DEBUG` 無關（`BAT_DEBUG` 只控制 `isDebugMode` 的 debug UI，`electron/preload.ts`）。userData 根部若有舊版留下的 `debug.log`，啟動時搬到 `Logs/debug-legacy-<stamp>.log`。
- **啟動期日誌（T0485）**：磁碟日誌由 `electron/app-paths-bootstrap.ts` 在 `setPath('userData')` 之後立即 `logger.init`（設定以 `logger.readSettings` 同步讀 `settings.json`），早於所有其他模組主體；whenReady 的 `logger.init` 為冪等（已初始化只重套設定，不重開檔、不重複輪替），一次啟動只產生一個 `debug-*.log`。bootstrap 同時呼叫 `installEarlyCrashCapture()`（`electron/early-crash-log.ts`）：
  - `uncaughtExceptionMonitor` → `[CRASH] early <origin>: …`；main.ts 註冊自己的 `uncaughtException` / `unhandledRejection` 後呼叫 `handOffEarlyCrashCapture()` 移除，不重複記錄
  - `console.error` 鏡像（`logger.mirrorConsoleErrors`）→ `[console.error] …`，到 whenReady 的 `endEarlyCrashCapture()` 為止。Electron 41 對主 bundle **載入期同步丟錯**不發 `uncaughtException`，而是 `console.error('App threw an error during load')` + stack 後讓行程無視窗存活；Node 的 `UnhandledPromiseRejectionWarning` 也走 `console.error`。鏡像是這兩者進磁碟日誌的唯一管道
  - **不得**在 main.ts handler 之前註冊 `uncaughtException` / `unhandledRejection` listener：前者會關掉 Electron 預設錯誤對話框（它只在 listener 數為 1 時顯示），後者會抑制 rejection warning（Electron 為 warn 模式）
- **GPU 狀態日誌 `[gpu]`（T0533 / BUG-136）**：`electron/gpu-status-log.ts`，main.ts 接線，只記錄、不改任何繪圖行為。`[gpu] info:` = `app.getGPUInfo('basic')` 精簡（每顆 GPU 的 vendor / device / 名稱 / driver、`active`）；`[gpu] feature status:` = 基準，在**第一次 `gpu-info-update`** 才記（之前 `getGPUFeatureStatus()` 回的是佔位值，全部 `disabled_software` / `disabled_off`，Windows whenReady 實測；15 s 內沒有 update 則記 `feature status (no gpu-info-update yet):`）；GPU 行程 `child-process-gone` 時在原 `[CRASH]` 行（格式不變）之後記 `[gpu] crash #N this session`、`feature status at crash:` 與 `changes since last logged:`；之後 `gpu-info-update` 只在狀態改變時記 `feature status changed: <key: 前 → 後> | <全部 key>`。判讀：`gpu_compositing` / `rasterization` / `2d_canvas` 為 `enabled` = 硬體繪圖；`disabled_software` / `unavailable_software` = 已退回軟體繪圖（CPU 負擔，畫面由 CPU 合成）；`disabled_off` / `unavailable_off` = 該功能關閉。Chromium 在 GPU 行程反覆崩潰後會整體退回軟體（隔離實例以 `chrome://gpucrash` 實測：第 3 次崩潰起全部變 `disabled_software`）。
  - **macOS 預設停用 Skia Graphite（T0669 / BUG-164）**：Electron 41（Chromium 146）的 Graphite 在 `graphite_shared_context.cc:291` CHECK（`kOutOfOrderRecording`）讓 GPU 行程崩潰。main.ts 在 darwin 加 `--disable-skia-graphite`（改走 Ganesh / ANGLE Metal），判斷唯一實作 `decideSkiaGraphite`（`electron/gpu-status-log.ts`）。🔴 用獨立的 switch，**不得**改成第二個 `appendSwitch('disable-features', …)`：同名 switch 後者覆蓋前者，`disable-features=ServiceWorker` 會失效（`electron/__tests__/skia-graphite-switch.test.ts` source guard）。逃生口：env `BAT_SKIA_GRAPHITE=1`（只認 `1`）不加 switch。Windows / Linux 不加任何 switch。啟動時記一行：`[gpu] skia graphite: disabled (darwin default, --disable-skia-graphite; BAT_SKIA_GRAPHITE=1 keeps it on)` / `[gpu] skia graphite: not disabled (BAT_SKIA_GRAPHITE=1)` / `[gpu] skia graphite: not disabled (platform=<platform>)`。判讀：停用生效時 macOS 的 `[gpu] feature status` 中 `skia_graphite=` 不再是 `enabled_on`。逃生口用法（macOS）：結束 BAT 後在終端機直接執行 `BAT_SKIA_GRAPHITE=1 /Applications/BetterAgentTerminal.app/Contents/MacOS/BetterAgentTerminal`（從 Dock / Finder 開啟不會帶這個 env；`open -a` 是否轉送 shell env 未實測），確認日誌出現 `skia graphite: not disabled (BAT_SKIA_GRAPHITE=1)`。
  - **GPU 行程崩潰後重建可見終端（T0669 / BUG-164）**：GPU `child-process-gone` 時 main 對所有 BAT 視窗（含 detached）送 `system:gpu-process-gone { crash: N }`（N 與 `[gpu] crash #N` 相同，原日誌不變）；`TerminalPanel` 只對 `isActive` 的終端在 canvas 可用後 `clearTextureAtlas()` + `refresh(0, rows - 1)`。時機：圖層 canvas（`.xterm-screen canvas`）的 `contextrestored`，或每 250 ms 檢查到沒有圖層 canvas `isContextLost()`（restore 可能早於這則訊息），最多等 5 s；視窗隱藏（最小化）時等 `visibilitychange` 顯示後才開始。同一個 N 只處理一次，等待中再來的崩潰合併成一次，兩次重建至少間隔 1 s。隱藏的終端不做事，切換過去時由 isActive effect（Win11 修正，未改）重繪。renderer 日誌：`[gpu] terminal redraw scheduled terminal=<id> crash=#N` → `[gpu] terminal redraw after GPU crash terminal=<id> crash=#N trigger=contextrestored|settled|timeout`（等待期間切走則 `[gpu] terminal redraw skipped (no longer active) …`）。`trigger=timeout` 表示 5 s 後仍有 canvas 回報 context lost，照樣重建。驗證：`src/__tests__/terminal-gpu-crash-redraw.test.tsx`。
- **單一 userData 目錄**（BUG-119，T0480 起）：`settings.json` / `windows.json` / `profiles/` / `Local State` / `snippets.json` / `message-archives/` / `helper-capabilities.json`（T0576，本機 PTY 範圍權杖的 digest 紀錄，見「遠端 Tower 通知」節的「本機 PTY」）/ `Logs/` / `Crashes/` 全在 `<appData>/BetterAgentTerminal[-runtime-<N>]/`（`--runtime=<N>` / `BAT_RUNTIME=<N>` 實例為 `BetterAgentTerminal-runtime-<N>`）。T0480 前 `snippet-db` 單例在 import 期呼叫 `app.getPath('userData')`，Chromium PathService 把 userData 快取成 `package.json` `name`（`better-agent-terminal`），日誌 / snippets / `Local State` 因此落在小寫目錄。現由 `electron/app-paths-bootstrap.ts` 依序 `setName` → 解析 runtime id → app ready 前同步 migration（`electron/userdata-migration.ts`）→ 顯式 `app.setPath('userData', ...)`；`main.ts` 在 `setPath('crashDumps')` 後自檢 userData 未漂移（不符即 `logger.error`）。**開發規則**：① `app-paths-bootstrap` 必須維持 `main.ts` 的**第一個** import（rollup 把被 import 模組的主體排在 `main.ts` 主體之前），且它只 import `electron` / `path` / `./userdata-migration` / `./logger` / `./early-crash-log` / `./early-path-fix`（後三者各自只 import fs / path / child_process / `./logger`；`app-paths-bootstrap-order.test.ts` 靜態守住）；② 任何模組**不得在 import 期**呼叫 `app.getPath('userData')`（含模組層級單例的建構子），一律在函式內 lazy 取值（範本：`snippet-db.ts` 的 `dataPath` getter）。`electron/__tests__/app-paths-bootstrap-order.test.ts` 靜態守住 ①。**macOS GUI 啟動 PATH 修正**（T0485）在 `electron/early-path-fix.ts`，由 bootstrap 在 early capture 之後呼叫（早於所有其他模組主體）；先前寫在 `main.ts` 頂部，實際晚於所有 import 的模組主體。**舊目錄**：升版首次啟動複製 `Local State`（缺才複製）、複製 / 合併 `snippets.json`、單檔移動 `message-archives/*.jsonl`，`Logs/` / `Crashes/` 不搬；runtime 實例整個目錄改名（terminal server 仍在執行或 rename 失敗時本次沿用舊目錄）；完成寫 marker `.userdata-migration.json`（只跑一次）。舊 `<appData>/better-agent-terminal[-runtime-<N>]/` 一律保留不刪（降版安全，舊日誌在那裡）；結果在 `logger.init` 後以 `[userdata-migration]` 寫入日誌。
- **Helper scripts 的 userData**（T0481）：本機 PTY（Terminal Server `pty:create`、node-pty、child_process fallback 三條路徑，`electron/pty-manager.ts` `localHelperEnv()`）注入 `BAT_USER_DATA` = `app.getPath('userData')`，覆蓋繼承值與 `customEnv`；只在 host 提供 `helperDir` 時注入（headless PTY 不注入）。`scripts/_bat-cert.mjs` / `scripts/_bat-logger.mjs` 解析順序：① 明確 override（`BAT_SERVER_CERT_PATH` / `BAT_HELPER_LOG_DIR`，headless bat-server 設定；`BAT_HELPER_LOG_DIR` 同樣須為絕對路徑，相對路徑忽略、改走 ②（`_bat-logger.mjs` `resolveLogPath`）；`BAT_SERVER_CERT_PATH` 有值即照用）→ ② `BAT_USER_DATA`（須為絕對路徑，相對路徑忽略）→ ③ 舊推測 `BetterAgentTerminal` + `BAT_RUNTIME`（T0481 前的 BAT 或 BAT 外執行）。`--runtime=<N>` 啟動的實例 PTY 沒有 `BAT_RUNTIME`，靠 ② 找到該實例自己的 `server-cert.json` 與 `Logs/bat-scripts.log`。本機 PTY 的 `BAT_REMOTE_TOKEN` 自 T0575 起是該 PTY 的範圍權杖（`batcap.`），helper 照舊讀這個變數名（不分辨權杖種類）；本機不注入 `BAT_SERVER_CERT_PATH` / `BAT_HELPER_LOG_DIR` / `BAT_HELPER_NODE`（headless 專用）。主行程日誌 `[helper-cap] issued: terminal=<id> role=tower|worker tower=<id>` / `[helper-cap] revoked: terminal=<id>` / `[helper-cap] not issued: …`（只記 id 與角色，不記權杖）。
- **PTY env 唯一組裝點**（T0525 / BUG-131）：`PtyManager.buildPtyEnv()`（`electron/pty-manager.ts`）供第一次建立（三條 spawn 分支）、`pty:restart`、Terminal Server recovery 共用；instance 記 `customEnv` / `workspaceId` / `agentPreset`，重建時沿用，helper 值（port / token / `BAT_USER_DATA`）在呼叫當下重新取得。新增 env 一律改這個函式，不要在分支內聯。**T0575**：`BAT_REMOTE_PORT` / `BAT_REMOTE_TOKEN` 只來自 host 的 `helperEnv`（本機 = `buildLocalHelperEnv`，該 PTY 的 `batcap.` 權杖，見「遠端 Tower 通知」節的「本機 PTY」），不再是 RemoteServer 的 server token（`PtyManager.getRemoteServerInfo` 已移除）；繼承來的 `BAT_REMOTE_*`（BAT 套 BAT）在 `helperEnv` 沒給時刪除（`customEnv` 明確給的保留），Terminal Server fork 的 env 也去掉（`terminalServerInheritedEnv`，`electron/main.ts`，server 會把自己的 env 墊在每個 PTY 之下）。
- **塔台派工落點**（T0523 / BUG-129）：本機 `terminal:create-agent-command` / `create-with-command` 由外部 helper 呼叫時，落點與 `--agent default` 解析以 `--notify-id` 塔台終端在 window registry 所屬的工作區為準（`electron/dispatch-workspace.ts`），`--workspace` 為 fallback，不一致時 `logger.warn` `[T0523]`；兩者皆無仍落在 active workspace（T0137）。遠端 headless 由 client renderer 的 `addExternalTerminal` 依塔台終端判斷。`bat-terminal.mjs` 成功時在 `✓ Terminal created` 之後印 `workspace:` / `agent:` 實際落點。已知限制：agent CLI 自己還原舊環境（例如 Codex 接續別的分頁開的 thread）時，`BAT_TERMINAL_ID` / `BAT_WORKSPACE_ID` 兩者都可能指向別的分頁，BAT 無法從 env 修正。**cwd 檢核（T0527 / BUG-132）**：main 解析出落點後，比對派工 cwd 與落點工作區 `folderPath`（`checkDispatchCwd`，`electron/dispatch-workspace.ts`；win32 / darwin 不分大小寫，原路徑與 realpath 都比，realpath 逾時 300 ms 即只比原路徑）：在底下 → 照舊；不在任何工作區底下 → 建立 + 警告（跨專案派工不擋）；在**另一個**工作區底下（取最深者）→ 非 yolo 建立 + 警告，`--mode yolo`（`customEnv.CT_MODE`）**拒派**，回 `{ ok:false, code:'DISPATCH_CWD_OTHER_WORKSPACE' }`，helper exit 1 並列出兩個工作區。落點工作區無 `folderPath` / 解析不到 / cwd 非絕對路徑 → 跳過。日誌 `[BUG-132]`，`bat-scripts.log` 事件 `dispatch-cwd-check`（`status` / `action`）。cwd 只做檢核，**不是**落點規則（T0137 不變）。遠端 headless 不檢核（server 沒有 client 的 `folderPath`）。**`--agent` 簡寫**：`normalizeAgentAlias`（`electron/terminal-command-handlers.ts`）只映射到 registry 已知 id（原 id → 小寫 → `<id>-cli`，例 `codex` → `codex-cli`）；仍不認得 → `{ ok:false, code:'AGENT_UNKNOWN', knownAgents }`，helper exit 1。headless 權杖的 `isKnownAgent` 以正規化後的 id 查 registry（T0450 範圍不變）。
