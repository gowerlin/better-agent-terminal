## 0. 摘要與推薦

4 份 CT 文件可以替網站補上兩類內容，第一版故事章節都沒有：

1. **越用越懂你的專案**：塔台學會專案規則，經驗慢慢長成標準流程；教戰手冊教 Agent「什麼情境用什麼做法」；視覺規範從程式碼抽出來。故事章節講的是一個早上；這些能力講的是第三個月。
2. **現實比計劃更混亂時**：臨時插隊、卡住就停（熔斷）、問題一層一層冒出來（洋蔥式）、兩邊一起改、塔台被慣壞。這些內容能讓第二根支柱「自動，但不失控」更有說服力。

**推薦**（細節見 § 4、§ 6）：

- 首頁在「自動，但不失控」之後加**一段**「越用越懂你的專案」：3 張卡片加 1 條成長管線，每張卡附一句「BAT 自己就是這樣用」。不另開大段，以免拉長首頁 60 秒的閱讀時間。
- `/control-tower` 增加 3 節：「塔台的分工原則」「現實比計劃更混亂時」「越用越懂你的專案」，FAQ 加一題「塔台被慣壞怎麼辦」。
- 另開 **`/cases`**：3 個去識別化情境案例和 2 個 BAT 自己的真實案例，沿用 C 的故事章節版面。排在 W2b 之後，作為獨立工單（W2d）。
- 7 張候選裡有 4 張可以直接上站，3 張需要改寫或由使用者確認。「資深開發者除錯模式分析」**整份不用**，因為它含有真實客戶與系統細節。

#### C1　合併之後，問題一層一層冒出來（約 195 字）

> 同事合併了一個大分支，`demo-shop` 的結帳 API 就壞了。你修好一個設定，服務起來後又冒出別的錯，接著建置流程也失敗；你開了三個對話各追一段，沒有一個看得到全貌。

#### C2　兩個服務，同一個欄位（約 170 字）

> `demo-shop` 的訂單服務會發出「訂單成立」事件，通知服務負責接收。你要把事件裡的 `createdAt` 改名為 `placedAt`，先讓 Agent 改好訂單服務，再叫它「照著改」通知服務。上線後才發現，一邊的欄位叫 `placedAt`，另一邊卻變成 `placedTimestamp`。
